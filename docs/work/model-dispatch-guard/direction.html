0.133.0 — the explicit-model dispatch contract

A delegated job used to inherit whatever model the caller was running, because naming it was a note rather than a requirement. Now the call names both halves — and one real mixed-model fan-out shows three different models actually running from one dispatch.

What changed

A note became a requirement

  • The guidance said the call "still passes model" — so every job omitted it.
  • Now: model picks Haiku, Sonnet, Opus or Fable; subagent_type picks the effort.
  • There is no unplanned dispatch: if you are calling Agent, the call is the plan.

What the fan-out showed

Three models, one dispatch

  • Requested haiku, sonnet, opus; observed exactly those three.
  • With CLAUDE_CODE_SUBAGENT_MODEL unset, as here, the same calls without a model would have resolved to the controller's Opus.
  • Effort observed as requested on the Sonnet and Opus jobs.

What it does not settle

The gap, stated

  • The Haiku job returned no effort records, so its effort stays unverifiable.
  • This is instruction text at the point of use; nothing blocks a dispatch mechanically.
  • A SendMessage resume carries no new pair — though a named model does persist into it.
