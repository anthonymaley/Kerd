Green here, red in CI.

The same tearDown line behaves two ways, decided by a unittest.mock guard that exists in one Python and not the other. Verified by experiment, not inferred.

WHAT IT COST BEFORE THE FIX

0.133.2 had repaired the symptom, not the leak

That release made the failing test capture the real class at import as REAL_RPC, so it stopped depending on the module attribute. CI went green while the leak was untouched.

Measured through the real runner before the repair: 692 of 730 tests ran while agent.RPC was leaked and 53 actually read it. Nine sit outside the family that manages the attribute — six in PartnersReaderTests, which has no patch site at all. On CI the leaked value is a permissive MagicMock, so they passed while reading it. No verdict ever changed.

APPLIED · UNCOMMITTED

The fix, and what holds it

daemon() now records that it suspended the parent's patcher, and tearDown restarts it only then. The except RuntimeError: pass is deleted, so a future double start surfaces instead of hiding. is_started could not carry that state — it does not exist on the CI Python.

FixtureIsolationTests, in the same module, asserts the invariant with the guard removed so it is checked the way CI behaves. It fails when the old tearDown is restored. 731 tests green both as shipped and under the emulated CI Python, where the probe now reports no leak.
