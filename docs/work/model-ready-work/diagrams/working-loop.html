Understand → Shape → Agree → Deliver: the loop shown below → Complete
  1. Your agreement

    The outcome, required proof and boundaries.

  2. Conductor prepares a focused job

    A suitable model, effort and prompt. Only relevant context.

  3. A model does the work

    It chooses the method within the agreed boundaries.

  4. An independent model reviews

    The actual result is checked against your original agreement.

  5. Conductor uses the findings

    Inspect, correct and prove. If work remains, return to preparing a focused job—without another routine “okay.”

  6. Complete, with proof

    The agreed outcome is met. Final user acceptance happens if agreed.

A material change or a decision the facts cannot settle comes back to you. Three different unsuccessful corrections trigger reassessment, not an endless loop. Limits are optional; publishing is separate unless authorized.

What makes this lightweight
  • One work record carries the agreement, decisions, activity and evidence.
  • The candidate carries the model connection. No project CI, custom hooks, copied session IDs, seals or approval hashes.
  • Local official guidance helps Conductor prepare the job. It does not guarantee an optimal model or a better result.
  • Switch preserves useful memory and the exact next action. Git save/pickup uses the agreed authority; a local-only save stays local.
What is still not proved

The refreshed whole conversation still needs a real-person check. No comparative speed/cost/quality or Windows-support claim is made. The bounded laptop trial used a user-opened destination session and a manually returned result; remote startup and native conversation migration are not implemented. Other installed Kerd skills have not been migrated. The CLI adapter uses existing authenticated accounts, Git, Python and macOS/Linux process controls.
