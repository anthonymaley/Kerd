## The interface

The [journey guide](skills/conductor/references/journey.md) contains the maintained
layouts and examples. The visible order is:

Journey and working brief → what is settled → current answer/visual
→ a necessary question or authorized action → what follows.

During delivery, the working view includes a short list of actual jobs and their
states. The person sees what is complete, what is working and what happens next.
No fabricated progress percentage, ETA, model activity or guaranteed question count.

Visuals can start during outcome, audience or scope understanding and evolve with
the answers. They explain the work itself, not only the process. They stay optional
where prose is clearer, and partial drawings remain visibly partial. A visual
does not add approval requirements or need a running web service.

Short acknowledgements and real implications make answers consequential. Progress
updates reveal real work. We do not manufacture insights or delay work for theatre.
The person may prefer a quieter or more detailed view; essential decision context
and actual state remain visible either way.

## What must be demonstrated

- A person can locate the current question, its proposed answer and consequence
  without reading an update essay; a question isn't hidden in a blockquote.
- The view makes stage, settled direction, the current issue and next action obvious.
  It does not present the ten internal areas as ten required user answers.
- A relevant early visual clarifies scope without inventing an approved design.
- A permitted simple yes advances work, not a second confirmation of the answer.
- Required plain-text questions and forbidden numbered choices preserve the
  surrounding answer/progress structure without pretending unsupported controls.
- Real activity changes the work view; an idle or returned job is not shown running.

Static formatting checks are not proof of usability. A bounded independent
forward-test checks behavior; the user's next real interaction must still establish
whether this feels better. No speed or resource improvement is claimed from this edit.

## Parked direction: a spoken companion — 2026-09-06

User inspiration: their experience of ChatGPT voice. The desired future interaction
is an interview that feels like two people talking, alongside—not replacing—the
CLI. Speech input and spoken responses are means to that experience, not a request
to read the current text-heavy interface aloud.

Keep the same work, saved understanding, authority and decisions across spoken
and typed interaction. Visuals remain useful on screen while the conversation
continues: what we are making, where we are, and what an answer changed. Moving
between voice and typing should not restart the interview.

Status: parked product direction, not part of the current build or a verified
capability. No provider, architecture or delivery commitment selected. Before
promoting it into work, investigate conversational latency, interruption and
correction, transcription errors around consequential decisions, microphone and
recording consent, privacy/retention, accessibility and cost. Do not add those as
new burdens to the current CLI flow.
