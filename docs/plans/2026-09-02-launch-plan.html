Five gates between here and a real user

Launch means one person, working in their own repository, drives a real work item from frame to acceptance — without editing Kerd's internals and without hand-authoring artifacts nobody documented.

The clean pilot is the launch criterion. The first pilot is an instrument, not evidence that Kerd is ready.

Two numbers retired from launch reporting

Both were true. Neither measures readiness, and reporting them as progress is how a system stays internally coherent while never meeting a user.

  • 91.6% Pieces landed against pieces written. It counts execution against contracts we wrote ourselves — and 14 of 33 work items have no contract at all, so they are in neither half of the fraction.
  • 1 of 7 Question sets. It measures one subsystem of one skill, not the product. Unchanged for the last 24 hours in any case.

The plan

Milestones alternate between two repositories. Every lane crossing is work that has never once been done — Kerd has never run outside its own tree.

Progress, reported against outcomes

Not against historical Piece totals. Existing work is not discarded — it is the foundation beneath milestone 1 — but it has produced no external end-to-end evidence.

Inside milestone 1: four components, one already proven

Tested against a disposable git repository holding one work record and nothing else. Refusal is not unbuilt capability — it is built and externally proven. What is missing is the wiring that invokes it. The fourth component is a product decision, not a blocker.

Gate engine — route, check, audit, refuse

check widget scope     → exit 1  REFUSES
check widget viability → exit 0  passes
audit                  → exit 0  runs
route  widget          → full 7-rung table

All four with --root aimed at a foreign repo and no code change. The standing decision that a consuming project gets judgment but never refusal is wrong as written — and the one saying the tools are absent there is also wrong. They ship; they were unreachable.

Externally proven

Skill invocation wiring

All seven skill call sites use a bare relative path, so outside Kerd they hit No such file and the skill degrades to prose silently. ${CLAUDE_PLUGIN_ROOT} appears in skill text zero times. Four of the seven need no code at all — only the plugin path and a --root.

Missing

Board and fidelity external targeting

progress.py accepts no --root — passing one prints usage and exits 2, so a consuming repo has no board and its position is unrecoverable. fidelity.py pins its root to the tool's own file path, so in a plugin cache it audits the cache: a silent wrong answer, not an error. Real code, two files.

Missing

Automatic CI or hook enforcement

No consuming-repo hook or workflow invokes the refusal independently. This is a separate product decision, not an assumed blocker. An interactive pilot is valid so long as Drive reliably invokes the gate and surfaces its refusal — launch waits on a second automatic channel only if that channel is explicitly part of the promised product.

Out of scope

The next decision

Which real product, and which small work item, for the diagnostic pilot.

Then scope reachability as the smallest prerequisite to start that pilot — not as a programme. Milestone 1 does not have to be complete to begin milestone 2; it has to be complete enough that the pilot's failures are the product's failures rather than the plumbing's.

Everything in milestone 3 stays deliberately unsized until milestone 2 returns findings. Sizing it now would repeat the mistake the derivation spike warned about — building from inspection instead of contact.
