## Key Decisions

- **Three-layer architecture model adopted.** Skills atomic, modes orchestrators, discipline gates universal. Cross-skill references in flow terms are forbidden at the skill layer — modes own all flow. Two exceptions remain: structural primitives (switch → kivna save) and discipline gates (universal via skill description triggers, no per-mode configuration needed). This dissolved the original "skills as islands" framing.
- **Capability-first format, skill names deferred.** Mode files describe capabilities (id + description) without naming which skill fulfills them. Skill mapping is a separate layer defined post-mode-design. This is the more disciplined version of capability-first — forces precise capability articulation, defers skill-catalog presupposition, and enables open-source portability across heterogeneous skill catalogs.
- **Plugin split: Kerd modes-only.** 9 atomic skills move to `kerd-skills` plugin. The split is the structural expression of "modes are portable contracts, skills are interchangeable implementations." Positioning shift: "Install Kerd to get the workflow framework; bring your own skills." Provisionally locked, gated by cross-plugin call verification.
- **Mode set: 16 modes, redefined.** User reorganized from 10 mixed shape/domain modes into 11+5 explicitly shape-based modes plus sales as the lone retained domain mode. Project-manage added as a queryable shape (different from flow-and-complete). Three new chains made visible: idea → interrogate → plan → execute → maintain; research → strategy → writing; sales ↔ writing ↔ call transcript ↔ peer review.
- **Mode 1 and Mode 3 full specs as worked examples.** Pattern: modes that orchestrate multiple lighter capabilities (new idea: 11 steps) are longer than modes that wrap a single heavy capability (interrogate: 7 steps). Both shapes work in the same format. Brief-to-spec compression is real: interrogate brief had 5 phases, full spec collapses to 4 because recitation lives inside the adversarial-interview capability's exit gates.

## Gotchas

- **The capability-first format can regress to skill-name framing if you're not deliberate.** Twice in this session I drifted: first the brief format named recommended skills, then the full spec frontmatter re-introduced `core_skills:`. Both required correction. The discipline is: skills are out of scope until mode design completes. If you find yourself writing a skill name in a mode file, that's the signal you've drifted layers.
- **Step Do fields can leak skill internals.** Mode 1's first draft had step 1's Do field listing what switch reads internally ("pull, read TODO.md Current Session block, read vault Status"). That's switch's job — the mode should say "Invoke session-boundary capability with 'open' semantics" and let the skill handle which files get read. If a skill changes its internals later, modes shouldn't break.
- **Re-numbering between mode list and suggested sequence creates confusion.** I had mode #2 = plan in the mode list, but mode #2 = interrogate in the suggested sequence. When the user said "lets do 2," interpretation was ambiguous. Fix: either align the orderings or always reference modes by name, not number, in conversation.

## Insights

- **The capability inventory is the actual artifact this session produced.** 35 capabilities across 16 modes, with 12+ recurring. Recurring capabilities are where skill investment has highest leverage — they're what the skill assessment phase will target first. Single-occurrence capabilities are weaker signals (could fold into broader skills or stay as inline actions). This inventory wouldn't have been visible without going mode-by-mode; it emerges from the work, not from speculation.
- **Mode-by-mode-then-skills sequencing is structurally right.** Doing skill design before knowing what skills are FOR (in the new architecture) is working in the dark. The capability map produced by mode design is the input that makes skill assessment honest: each skill gets evaluated against concrete demand, not speculation. This collapses M2 (mode authoring) into the design pass — design becomes the implementation spec.
- **Skill-name deferral is structurally different from capability-first-with-recommendations.** Both look similar but they're not. With-recommendations: "here's the capability and here's the skill we lean toward." Deferred: "here's the capability, period." The deferred version forces precise capability articulation because the skill name isn't there to absorb ambiguity. The downstream skill assessment phase then has a clearer contract to match against.
- **Heavy-capability modes are thinner; light-capability modes are longer.** Interrogate (heavy adversarial-interview capability) compressed to 7 steps; new idea (4 lighter capabilities) needs 11 steps. The format absorbs both shapes. Pattern worth watching as we expand the other 14 modes — modes wrapping heavy capabilities (problem analysis around sensei:work, peer review around receiving-code-review) should also be thin.
- **The provisional lock + gating pattern works for high-impact decisions.** Plugin split was locked provisionally but gated by M12 (cross-plugin call verification). This lets design proceed without waiting for verification, but signals where the design might need rework. Better than either blocking on every verification OR committing without checking.
