## The diagnosis, and what it cost before the fix

`FinalReviewTests.tearDown` restarted a patcher its own `daemon()` had not stopped. From
CPython v3.12.8 that double start raises `RuntimeError("Patch is already started")`,
which the fixture swallowed; below v3.12.8 there is no such guard, so it silently
succeeded, re-saved the current MagicMock as the original, and the parent's single
`stop()` restored the mock. CI's ubuntu-24.04 runs 3.12.3. That is the whole asymmetry:
green here, red there.

Measured through `tools/run_tests.py` itself with the guard removed: **692 of 730 tests
ran with a mocked `agent.RPC` and 53 actually read it** — 44 inside the family that
manages the attribute, where the probe entangles with their own juggling, and **9
outside it** (`PartnersReaderTests` 6, which has no patch site at all, plus `ArrivalTests`,
`SessionIdentityTests`, `QueueTests`). No `conductor` or `switch` test touched it.
**No verdict ever changed**, which is exactly why a green suite hid it. After the fix the
same probe reports no leak, 0 exposed, 0 uses.

0.133.2 had repaired only the symptom — the failing test stopped reading the module
attribute. The cause survived that release untouched.

## Codex's finding, and why it mattered

`FixtureIsolationTests` ran four test classes nested but **discarded each `TestResult`**,
so it could have reported green over hidden nested failures whenever the attribute
happened to end restored. Accepted and fixed. The negative control proves it was real:
with a nested failure induced, `agent.RPC` ended restored, so the attribute assertion
alone would have said green.

Both negative controls are the point. A regression test that only ever passes proves
nothing about whether it would catch the defect returning.
